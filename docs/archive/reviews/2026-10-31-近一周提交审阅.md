## 必须修

### 1. `.xml` 仍以 `application/xml` + `inline` 直出，可在分享域上执行脚本（存储型 XSS，公网无登录门）

- 位置：`src/server/routes/file.ts:72`（`UNSAFE_INLINE_TYPES` 只含 `text/html`、`application/xhtml+xml`、`image/svg+xml`）；`src/server/routes/dir.ts:435-438`（同一判定复制了一份）；`src/shared/mime.ts:6`（`'.xml': 'application/xml'`）。
- 问题：浏览器把 `application/xml`/`text/xml` 文档当 XML 文档渲染；只要文件里带 XHTML 命名空间元素（`<html xmlns="http://www.w3.org/1999/xhtml"><script>…`）或 `<?xml-stylesheet?>` 指向 XSLT，脚本就会在 `z.imjp.uk` 这个与 `/dashboard`、`/revoke` 同源、带 owner cookie 的域上执行。这正是 9 月 `pr/raw-content-security` 要堵的那类洞，但 XML 漏掉了。本周的 Range/HEAD 改动没有引入它，但 `rawFileResponse` 被重写时沿用了这个集合，`HEAD` 也原样返回同样的 `Content-Type`。
- 证据：探针实测 `GET /f/<token>/raw`（文件 `evil.xml`，内容为 XHTML 命名空间 + `<script>`）→ `200`、`content-type: application/xml`、`content-disposition: inline; filename="evil.xml"`。`/d/:token/raw` 代码路径同一判定（`dir.ts:434-457`），结论相同。页面路由 `/f/<token>` 走 code 渲染器输出转义后的 HTML，不受影响；只有两个 raw 路由直出。
- 建议修法：把 `application/xml`、`text/xml`（以及 `application/xslt+xml`、`application/mathml+xml` 等 `+xml` 后缀）并入 `UNSAFE_INLINE_TYPES`，与 HTML/SVG 同样降为 `text/plain; charset=utf-8` + `attachment`；或更稳妥地改为白名单：只有图片（非 SVG）、音视频、PDF、`text/plain`/`text/markdown`/`text/csv` 允许 `inline`，其余一律 `attachment`。两处判定应合成一个共享函数（如 `mime.ts` 导出 `isInlineSafe(mime)`），避免 `file.ts` 与 `dir.ts` 再次漂移。补测试：`tests/file-render-size.test.ts` 和 `tests/dir-raw-content-security.test.ts` 各加一条 `.xml` 用例（断言非 `*/xml` 类型且 `attachment`）。

## 建议修

### 2. 空闲超时关闭范围过宽：整段 `/f/`、`/d/` 前缀，不限媒体、不限鉴权通过、无上限

- 位置：`src/server/serve.ts:15-23`（`STREAMING_PATH = /^\/(f|d)\//`，命中即 `server.timeout(req, 0)`，发生在路由与鉴权之前）。
- 问题：
  - 命中的不只是文件字节流，还包括 `/f/:token` HTML 页面、`/d/:token` SPA 页、`/d/:token/api/tree`、`/d/:token/api/git/*`、`POST /d/:token/api/git/unlock`（密码解锁）等 API，以及 token 不存在的 404 和被限流的 429 请求。PR #25 描述写"dashboard 和 API 端点保持默认"，对 `/d/` 下的 API 不成立。
  - `0` 在 Bun 语义里是"无超时"（`node_modules/bun-types/serve.d.ts:1015`），没有任何替代上限。客户端只要发一个 `GET /f/任意串` 并不读响应，连接就一直挂着。DoS 本身不在本次范围，但"是否仅对媒体放开、有无上限"的答案是：都没有。
- 证据：`tests/stream-idle-timeout.test.ts:65-74` 的单元测试只断言 `/dashboard` 不调用、`/f/abc/raw` 与 `/d/abc/raw/x.mp4` 调用，没有覆盖 `/d/:token/api/*`；`grep` 确认 `dir.ts:249-364` 的 API 全在 `/d/:token/` 前缀下。
- 建议修法：（a）把判定收窄到真正直出字节的路径：`/f/:token/raw`、`/d/:token/raw`，以及 `/f/:token`、`/f/:token/:filename` 中走 `rawFileResponse` 的分支——后者在路由层不好判，可改为在 `rawFileResponse` 内按 `guessedMime` 是 `audio/*`、`video/*`、`application/pdf` 时才调用 `c.env`/传入的 `server.timeout(req, 0)`，其余路径保持默认；（b）不用 0 而用一个大但有限的值（如 600 秒），暂停播放超过十分钟再续读本来也要重新发 Range。（c）同步改 PR #25 描述与 `serve.ts` 顶部注释。另：`server.timeout(req, 0)` 对同一 keep-alive 连接上的后续请求是否复位为默认，本次未验证，建议在修改时顺手用真实套接字测一下。

### 3. 目录分享的 raw 路由没有同步补 Range / Accept-Ranges / Content-Length，Safari 在目录分享里仍播不了视频

- 位置：`src/server/routes/dir.ts:422-458`（`readFileSync` 整文件读入内存后 `new Response(data, …)`，无 `Accept-Ranges`、不解析 `Range`、不处理 HEAD）。
- 问题：PR #25 把 `/d/` 也纳入"媒体播放"场景（空闲超时对 `/d/` 一并放开），但 Safari 播放 `<video>` 的前置条件是服务器响应 `Range: bytes=0-1` 以 206（这正是 #21 追加修复的动机）。`/d/:token/raw` 收到 Range 会直接 200 整文件，Safari 仍判定不可 seek、通常拒播；另外整文件 `readFileSync` 对大视频等于把文件全读进内存（9 月已知遗留，本周没一起处理）。
- 证据：`dir.ts:440` `const data = readFileSync(absPath)`；`dir.ts:453-457` 响应头只有 `Content-Type`、`Content-Disposition`。
- 建议修法：把 `file.ts` 的 `parseRange` + `rawFileResponse` 抽到共享模块（如 `src/server/raw-response.ts`），`dir.ts` 的 raw 路由改为调用同一函数（它已经有 `validateDirPath` 做路径校验，只需把 `absPath` 传入）；`tests/file-raw-range.test.ts` 的四组用例对 `/d/:token/raw?path=` 再跑一遍。这也顺手消掉第 1 条里两份 `UNSAFE_INLINE_TYPES` 的重复。

### 4. 新测试没覆盖 Range 解析的关键边界与 8 MB 分块上限

- 位置：`tests/file-raw-range.test.ts`。
- 问题：已测 `100-199`、`9900-`、`-50`、`20000-30000`(416)、HEAD 200。没测：`bytes=-0`（应 416）、`start>end`（`bytes=5-2`，应 416）、多段 `bytes=0-1,2-3`（应回退 200 整文件）、0 字节文件任何 Range（应 416 `bytes */0`）、`end` 超出文件末尾时截到 `size-1`、HEAD + Range（应 206 + Content-Range + Content-Length、无体）、HEAD 与 GET 头部逐项一致、以及 `MAX_RANGE_CHUNK`（`file.ts:75`）截断路径——真实套接字测试用的是 3 MB 文件，`bytes=1000-` 永远到不了 8 MB 上限，`expect(lastServed).toBeLessThanOrEqual(end)` 这条"允许缩短"的断言实际从未被触发。
- 证据：探针实测上述全部边界结果均正确（`-0`→416、`5-2`→416、多段→200/CL=1000、空文件 `0-`→416 `bytes */0`、`0-99999999999999999999`→`0-999/1000`、HEAD+`10-19`→206/`bytes 10-19/1000`/CL=10/体 0 字节、HEAD 与 GET 头完全一致），所以这是覆盖缺口不是缺陷；但这些行为现在只靠人读代码保证。
- 建议修法：在 `file-raw-range.test.ts` 加一个表驱动用例覆盖上面 8 种输入；真实套接字测试改用 `9 MB` 文件并断言 `bytes=0-` 返回 `0-8388607/size`。

## 核实过无问题

- Range 解析（`file.ts:82-99`）：`parseInt` 超大数字（`99999999999999999999`）得 `1e20`，`start >= size` 判 416，`end` 被 `Math.min(…, size-1)` 截断，无整数溢出或越界读；`start` 永远 `≥0`（后缀形式用 `Math.max(0, size-n)`）；`end+1` 传给 `file.slice` 时 `end ≤ size-1`，不越界。实测 15 组输入结果全部符合 RFC 9110（见第 4 条证据）。
- 多段 Range（`bytes=0-1,2-3`）：正则不匹配 → `null` → 200 整文件，这是 RFC 允许的忽略方式，不会触发多体响应或放大。
- 路径穿越：`rawFileResponse` 的 `filepath` 只来自数据库 `row.filepath`（`file.ts:153,202`），不接收请求参数；`/d/` 的 `validateDirPath` 未改动。
- 206 的 `Content-Range`/`Content-Length`：`end = min(range.end, start+8MB-1)`，`length = end-start+1`，`Content-Range: bytes start-end/size`；探针与真实套接字测试均核对体长 = `Content-Length` = `end-start+1`。
- 416：`Content-Range: bytes */size`，无体，`Accept-Ranges` 仍带。空文件任何 Range → 416 `bytes */0`，符合规范。
- HEAD：Hono 4.12.9 `#dispatch` 把 HEAD 按 GET 路由并丢弃体（`node_modules/hono/dist/hono-base.js:273-275`），`c.req.method` 仍为 `HEAD`；探针逐项比对 HEAD 与 GET 响应头完全一致（`accept-ranges`、`content-disposition`、`content-length`、`content-type` 及安全头），HEAD + Range 返回 206 且体为 0 字节。HEAD 不泄露 GET 没有的信息。
- 整文件 200：`Content-Length: size` 显式设置，`Bun.file` 流式体；24 MB 暂停下载测试通过。
- 限流器隔离（`780c793`）：只改了 `tests/file-raw-range.test.ts`（每请求换一个 `198.51.100.x` 文档保留段 IP + `DROP_TRUST_PROXY=1`），`src/server/middleware/rate-limit.ts` 本周零改动；生产行为不变。
